# Raspberry Pi

How Omarchy runs on a Raspberry Pi: the `aarch64-rpi` platform family, the Pi firmware boot chain it drives through a platform boot package, the local repository its Omarchy packages are built into, the hardware setup it adds, what it leaves out, and how an SD-card image is built. The Pi 400 is the model this fork targets; the design and the reasons behind each decision are in [`plans/pi-400-port.md`](../plans/pi-400-port.md).

## Status

Everything here is covered by the shell suite, by full image builds on an x86_64 host (`pi/build-image` in a binfmt_misc chroot through qemu-user 10, about an hour each), and by booting a built image in QEMU's `raspi4b` machine with the Pi 400's device tree ([`pi/README.md`](../pi/README.md), Booting an image under QEMU). Under emulation, the image's first boot gave the card its own disk identifier before anything mounted it, grew the root to fill the card, ran the deferred hardware setup (the pacman keyring, every queued leaf, the boot files) and rebuilt the initramfs on the device; `update-verify` passed; a second boot from that initramfs, by the card's new PARTUUID, skipped first-boot setup with no unit failing; and the owner wizard waited on tty1 both times. With a keyboard on the SoC's USB controller, the owner wizard ran to the end under emulation too: it took the layout, the account, the hostname and the timezone, created the account with its home and git identity, finished the user's setup and handed off to SDDM. With a renewed card from the same image in the SD slot and a fresh one on USB, only the fresh one got a new identifier and booted. A release image built by the workflow, with a `pimarchy.txt` filled in on Windows (CRLF line ends, a quoted password with a trailing space) and no keyboard, set itself up headless under emulation: the headless unit set the hostname, timezone, Wi-Fi country and a Wi-Fi profile NetworkManager read back exactly, and turned SSH on; owner setup ran unattended and created the account with its git identity, keymap and authorized key; `ssh` with that key logged in over QEMU's USB network, password logins were refused, `pi400.local` resolved over mDNS, no unit failed, and the card's passwords were blanked in place. QEMU emulates no GPU, Wi-Fi or Bluetooth for this board, so SDDM finds no display, nothing from Hyprland on has run, and no Wi-Fi network was joined; none of it has run on a Pi 400 yet. The checklist at the end is what a first hardware run has to confirm.

## Platform

`omarchy-hw-platform` prints `aarch64-rpi` when the device tree's root `compatible` carries a `raspberrypi,` token: the Pi 400 is `raspberrypi,400`, `brcm,bcm2711`, a Pi 4 Model B `raspberrypi,4-model-b`, a CM4 `raspberrypi,4-compute-module`. A `brcm,` token alone is not a Pi, since other Broadcom SoCs carry it. A Pi device tree next to Apple, Qualcomm, N1x or GB10 evidence, or on an x86 CPU, is a contradiction and the detector fails. Feature code asks `omarchy-hw-aarch64-rpi`; a Pi 400-only quirk asks `omarchy-hw-match-device-tree raspberrypi,400`.

An image names `platform=aarch64-rpi` in its image-target manifest, so the build host's own device tree never decides anything while the image is built.

## Packages and repositories

The Pi composes the base list, `install/omarchy-aarch64.packages` and `install/omarchy-aarch64-rpi.packages` (`omarchy-pkg-defaults aarch64-rpi`). Its own list carries the boot chain and the board's hardware:

- `linux-rpi`, the Raspberry Pi Foundation kernel from Arch Linux ARM's core. Omarchy's own aarch64 kernel is built without BCM2711 support. Its headers are left out, since nothing in the default set builds kernel modules.
- `raspberrypi-bootloader` (the GPU firmware that boots the board) and `firmware-raspberrypi` (Wi-Fi and Bluetooth firmware for its Cypress radio), both from `[alarm]`.
- `raspberrypi-utils`, `rpi4-eeprom` for the bootloader EEPROM, `vulkan-broadcom` for the v3d GPU, and `wf-recorder` for screen recording.

Its pacman templates, `default/pacman/aarch64-rpi/`, are the aarch64 ones (`[omarchy]`, then Omarchy's mirror of Arch Linux ARM's `[core]`, `[extra]` and `[alarm]`) with one repository in front: `[pimarchy]`, a local `file:///var/lib/pimarchy/repo`. Upstream's aarch64 `omarchy` and `omarchy-settings` packages don't know the Pi, so the Pi builds those two, and its boot package, from its own Pimarchy checkout at `/var/lib/pimarchy/src`. pacman installs and upgrades a package from the first repository that carries its name, so the local builds win over `[omarchy]`'s without pinning anything, and every other package still comes from Omarchy and Arch Linux ARM.

`omarchy-update-rpi-pkgs` keeps that repository current. `omarchy update` runs it on a Pi before the package transaction: it fast-forwards the checkout, and when the checkout moved it builds the three packages from `pi/pkgbuilds/` as the updating user, versioned `<PKGBUILD pkgver>.r<serial>.g<sha>`, and publishes them. The serial is the checkout's commit count, or one past the highest serial the repository already holds when that is not lower, so a reset or rebase onto fewer commits still upgrades what is installed. With `--init` it only makes sure the repository exists, since pacman refuses to sync a `file://` repository without a database; everything that installs the Pi templates runs it first.

The checkout and the repository belong to root, so the command reaches them through the update's sudo authorization, while makepkg runs as the user (as root, it builds as `SUDO_USER` or as `--as-user <user>`). It builds in a fresh directory under `/var/tmp`, since a Pi's `/tmp` is in RAM, and publishes only once all three packages built: a failed build stops the update and leaves the repository as it was. A checkout with uncommitted changes, untracked files included, is neither fast-forwarded nor built, since the packages copy the working tree and would carry the changes under the name of a commit that lacks them: the update warns, names `sudo git -C /var/lib/pimarchy/src stash -u`, and goes on with the packages the Pi has, so commit a change to have it built. The checkout is blobless, so the fast-forward downloads the new commits' file contents; when that fails, the update puts the checkout back at the commit it was at, says so, and builds nothing. A checkout with local commits its upstream lacks, whether ahead of it or diverged from it, is built as it is, with a warning.

Nothing verifies the commits the checkout fast-forwards to: no signature is checked and `[pimarchy]` is unsigned (`SigLevel = Optional TrustAll`), so whoever can push to the tracked branch of the checkout's origin, the repository and branch the image was built from, decides what every Pi following it builds and installs as root at its next update. Push access to that branch is the Pi's root trust anchor, where upstream's `[omarchy]` packages rely on Omarchy's packaging key.

A channel change on a Pi keeps this `omarchy` pair, since `[omarchy]`'s `-dev` pair for edge doesn't know the Pi, so a Pi on edge reads as edge from its mirrors alone. `omarchy channel set dev` on a Pi clones Pimarchy into `~/omarchy` from the upstream of the branch checked out in `/var/lib/pimarchy/src`, and refuses an existing `~/omarchy` without the Pi's templates as not Pimarchy. Between updates, the bar's update indicator compares the commit the Pi last built with the tip of that branch.

Anything that rewrites a Pi's `pacman.conf` has to keep `[pimarchy]` first, or `[omarchy]`'s builds replace the Pi's at the next update. Migration 1791403252, which moves `[omarchy]` to the front of every `pacman.conf`, predates the Pi: owner setup marks every migration the image ships as done for the account it creates (`omarchy-provision-user --first-install`), so it never runs on a Pi.

The `omarchy` and `omarchy-settings` PKGBUILDs in `pi/pkgbuilds/` are upstream's, vendored from `omacom/omarchy-pkgs`; `pi/pkgbuilds/README.md` records the source and any local change.

## Boot chain

The Pi has no UEFI. Its firmware reads `config.txt` from the FAT partition mounted at `/boot`, loads `kernel8.img`, the board's device tree and `initramfs-linux.img`, and passes `cmdline.txt` to the kernel. `linux-rpi` owns `config.txt` and `cmdline.txt` as `backup=` files, so Omarchy edits them in place rather than replacing them. There is no Limine, no UKI, no snapper and no LUKS.

The initramfs comes from `linux-rpi`'s mkinitcpio preset, rebuilt by mkinitcpio's own pacman hook whenever the kernel changes. `etc/mkinitcpio.conf.d/00-omarchy-hooks.conf` gives the Pi its own baseline, `base udev plymouth keyboard autodetect modconf kms keymap consolefont block filesystems fsck`: no `btrfs-overlayfs`, which only `limine-mkinitcpio-hook` ships and whose absence makes mkinitcpio exit 1, no `microcode`, and no `encrypt`.

The Pi registers a platform boot package with `omarchy-lifecycle-dispatch`, as Apple Silicon does ([`lifecycle-dispatch.md`](lifecycle-dispatch.md)): `omarchy-rpi-boot`, with its operations in `/usr/lib/omarchy/rpi-boot/`. Its sources are `pi/rpi-boot/`.

- `setup-boot` runs as hardware setup's last leaf on every install and rerun, and on an image's first boot. It points `cmdline.txt`'s `root=` at the root partition's PARTUUID, adds the kernel parameters every Omarchy machine boots with (`KERNEL_CMDLINE[default]` in `/etc/limine-entry-tool.d/omarchy-defaults.conf`), keeps any parameter the user added, and maintains one managed block at the end of `config.txt` (`disable_splash=1`, plus the initramfs and `vc4-kms-v3d` lines if the file lacks them). It then rebuilds the initramfs when its inputs changed, or on an image's first boot asks the first-boot service to.
- `update-verify` runs at the end of `omarchy update` and proves the updated system boots: the installed `linux-rpi` kernel and modules are in `/boot`, the initramfs carries that kernel's modules, `config.txt` loads the initramfs, and `cmdline.txt`'s root is the running root and no other attached disk carries its PARTUUID. Until it passes, the update does not offer a reboot.
- Provisioning and factory reset keep the generic path. The Pi's root is unencrypted ext4, which owner setup handles directly and factory reset refuses (it needs btrfs).

`omarchy-rpi-grow-root.service`, also from the boot package, grows the root partition and its filesystem to fill the card on an image's first boot. It reads the layout from the partition table and sysfs rather than udev, whose database is still empty that early; a layout it can't read yet is retried on the next boot.

Every card flashed from one image starts with the image's MBR disk identifier, so with the same PARTUUIDs (`<id>-01`, `<id>-02`), and the same root filesystem UUID and boot volume ID. The first boot gives the card an identifier of its own, before udev or systemd see the disk: the image's `cmdline.txt` names the root by its filesystem UUID with `pimarchy.new_disk_id=<the image's identifier>`, and the boot package's `omarchy-rpi-disk-id` initramfs hook (in `HOOKS` through its `/etc/mkinitcpio.conf.d/90-omarchy-rpi-disk-id.conf`) picks, of the partitions with that UUID, the one on a card whose `cmdline.txt` still carries the flag, so a card renewed before can't stand in for it and a card whose first boot was cut short still counts, writes a random identifier into that disk's MBR and mounts the root by its device. A card on USB can show up after udev settles, so the hook waits for the flagged card as long as mkinitcpio itself waits for a root that doesn't show up, twice `rootdelay` (10 seconds unless set), and renews none when it doesn't appear; the boot then waits for the image's own root partition, `PARTUUID=<the image's identifier>-02`, which no card renewed before has, instead of mounting any card by the UUID they all share. Once the root is mounted it points `/etc/fstab`'s `/` and `/boot` at the new PARTUUIDs, then commits by renaming a new `cmdline.txt` into place, with `root=PARTUUID=<new>-02` and without the flag; `setup-boot` leaves `root=` alone while the flag is there. Until that rename the old `cmdline.txt` still holds, so a power cut means the next boot does it all again, and when fstab can't follow, the old identifier goes back. Only two cards from the same image whose first boots haven't both finished, attached together, can still be mixed up. `update-verify` also fails while another disk carries the root's PARTUUID and says to disconnect it, so `omarchy update` offers no reboot until it is gone. The hook's files live under `/usr/lib/initcpio`, so each update that rebuilds `omarchy-rpi-boot` also rebuilds the initramfs, about a minute on a Pi.

## Hardware setup

The Pi's own setup is small, and each piece lives where its kind of setup does:

- **Sleep.** `install/hardware/rpi/sleep.sh`: `linux-rpi` has no suspend or hibernation and the BCM2711 has no PSCI firmware to suspend its cores, so the leaf turns every sleep state off for systemd, and the menu hides Suspend, as on the GB10.
- **Network.** `install/hardware/network.sh`, the generic network leaf, retires Arch Linux ARM's stock systemd-networkd DHCP files (`en.network`, `eth.network`) on any machine, as it retires other distributions' stock files, so NetworkManager owns the interfaces. It only moves files that still hold the stock content.
- **Vulkan.** v3d is a device-tree platform device that `lspci` never sees, so `install/hardware/vulkan.sh` installs `vulkan-broadcom` by platform.
- **Display scale.** A Pi drives HDMI monitors at 1x, so user setup's `install/user/hardware/rpi/gdk-scale.sh` starts the user's `GDK_SCALE` at 1 instead of the shipped 2, and `omarchy-reinstall-configs` applies it again.

What already works on a Pi without a branch of its own:

- **Hyprland.** Aquamarine opens only KMS cards, so it scans out on vc4 and renders on v3d. Hyprland asks for GLES 3.2 and falls back to 3.0, which Mesa's v3d (GLES 3.1) gives it; only custom screen shaders written for `#version 320 es` won't compile.
- **Audio.** The Pi 400 has no 3.5 mm jack. Its device tree already passes `snd_bcm2835.enable_headphones=0` on the kernel command line, and the vc4 KMS overlay turns off the firmware's HDMI audio, so the only sound cards are vc4's two HDMI outputs.
- **Bluetooth.** The radio is a serial-device child of the PL011 UART, so the kernel's `hci_uart` attaches it with no service, and `firmware-raspberrypi` supplies `BCM4345C5.hcd`. Wi-Fi is the CYW43456, whose firmware also comes from `firmware-raspberrypi`.
- **The power key.** Fn+F10 sends `KEY_POWER`, which opens Omarchy's power menu, and shutdown cuts power through the board's poweroff GPIO.
- **Displays, brightness and power.** The monitor panel shows both HDMI outputs, DDC brightness works where the monitor supports it (failures are cached), power profiles fall back to the placeholder driver's balanced and power-saver, and the power panel hides itself with no battery.

## What is off, and why

| Feature | On a Pi | Why |
| --- | --- | --- |
| Limine, UKIs, Direct Boot | Not available; `omarchy-refresh-limine` and `omarchy-kernel set` say so, and the menu hides Direct Boot | No UEFI; the firmware boots `kernel8.img` |
| Snapshots | Skipped; `install/config/snapper.sh` does nothing without snapper and a btrfs root | ext4 root |
| LUKS, hibernation, factory reset | Not available | v1 image has an unencrypted ext4 root and no disk swap (only zram, which hibernation cannot use) |
| Firmware updates | `omarchy-update-firmware` updates the bootloader EEPROM with `rpi-eeprom-update` instead of fwupd | fwupd has no Pi support |
| Docker databases | MSSQL is offered on x86 only and MongoDB not on a Pi | No arm64 MSSQL image; MongoDB needs ARMv8.2-A, the Cortex-A72 is ARMv8.0 |
| Windows VM, x86 games | Hidden, as on every aarch64 machine | x86-only |

## Images

`pi/build-image` builds a flashable `pimarchy-*.img.xz` from Arch Linux ARM's Pi rootfs on an x86_64 or aarch64 host, without loop devices or lasting mounts: each command meant for the image runs in a chroot inside a private mount namespace, its aarch64 programs run through binfmt_misc and qemu-user on x86_64, or under proot where binfmt_misc can't be registered. [`pi/README.md`](../pi/README.md) covers running it and flashing the result. It follows the image-target contract every Omarchy image build uses: it writes the manifest naming `aarch64-rpi`, swaps U-Boot and `linux-aarch64` for `linux-rpi`, builds the local packages, installs the Pi's default set, runs `omarchy-apply-system --defer-provisioning --first-install` (which queues every hardware leaf for the first boot), writes the boot files for the image's own PARTUUIDs, arms owner provisioning, and seals the root.

On first boot the root grows to fill the card, `omarchy-provision-hardware` creates the pacman keyring and runs the queued hardware leaves offline, the boot package's `setup-boot` settles the boot files and the initramfs is rebuilt on the device, and the owner wizard on tty1 asks for keyboard, account, hostname and timezone before logging into Hyprland once.

A Pi with no screen is set up from `/boot/pimarchy.txt` instead, which the image ships with every setting empty, as DietPi's `dietpi.txt` (`pi/rpi-boot/pimarchy.txt`, installed by the boot package to `/usr/share/omarchy-rpi-boot/` and copied by the builder, which refuses an image whose copy differs). `omarchy-rpi-headless.service` runs `/usr/lib/omarchy/rpi-boot/headless` while `/var/lib/omarchy/provisioning/pending` exists, after `ufw.service` and before NetworkManager, Avahi, sshd, `omarchy-provision-hardware` and the owner wizard. It reads the file as data, never sourcing it, and only as plain text: a file with NUL bytes (UTF-16, which Bash would read with the NULs dropped while blanking missed every line) or lone CRs is reported and left unused. It checks each value against the owner form's rules (`install/provisioning/setup-form.sh`) and what owner setup checks besides (no account or group by that name, unless it is the one an interrupted owner setup already created and pinned; a zone or link in `tzdata.zi`, as timedated lists them), so owner setup takes whatever it stages, and writes: the Wi-Fi country into `/etc/conf.d/wireless-regdom`, which hardware setup's timezone-derived country then leaves alone; a NetworkManager keyfile, `pimarchy-wifi.nmconnection`, naming the SSID by its bytes; `/etc/hostname` and the running hostname, so DHCP and mDNS announce the owner's name from the start; `/etc/localtime`; and the account's answers in `/var/lib/omarchy/provisioning/answers` (root, 0600), with SSH keys in `authorized_keys` beside it. Owner setup finds the answers and runs unattended (`omarchy-provision-owner --unattended`), falling back to the wizard on tty1 if they fail its checks. With an account or a key, it enables and queues sshd, opens port 22 with `ufw limit` as `omarchy-setup-security-sshd` does, and with a key writes the same `10-omarchy-hardening.conf` that turns password logins off. However the run ends, from its exit trap, it overwrites each password line, empty ones included, and each line it couldn't read, in place with a comment of the same length, since renaming a new file over it would leave the old clusters on the card, and reports what it applied and skipped to `/boot/pimarchy-status.txt`. A rerun reads the blanked lines as absent and keeps the Wi-Fi profile and the account an earlier run staged, refreshing the account's other answers from the file; one that names another network or account without its password keeps the earlier one and says so.

## Hardware checklist

A first run on a Pi 400 has to confirm, in order:

1. The image boots to the owner wizard, and the root partition fills the card. With `pimarchy.txt` filled in instead, the Pi joins Wi-Fi with no screen attached and `ssh <user>@<hostname>.local` reaches the account it set up.
2. Hyprland starts on vc4 with the Quickshell bar, on one and on two HDMI monitors, at 1080p and 4K30.
3. `aplay -l` shows no Headphones card, and sound plays on each HDMI output.
4. Wi-Fi joins a network from the network panel, and Bluetooth pairs a device.
5. The cursor draws without corruption (if not, Hyprland needs `cursor:no_hardware_cursors`, also in SDDM's greeter config).
6. `omarchy update` rebuilds the local packages, `update-verify` passes, and the machine reboots into the new kernel.
7. A theme switch, a screenshot, a screen recording and the nightlight toggle work.
